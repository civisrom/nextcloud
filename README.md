# Nextcloud: Docker, Nginx на хосте, ручной nftables

Установщик для **Ubuntu 24.04 LTS и 26.04 LTS**, amd64/arm64. Один экземпляр
Nextcloud 35, PostgreSQL 17 и Redis. Docker и Nginx уже должны быть установлены.
Серверу рекомендуется от 8 ГБ RAM и достаточно места для данных и резервных копий:
сумма лимитов рабочих контейнеров составляет около 5,4 ГБ, память нужна также хосту.

**Проверка безопасности обязательна.** Установщик блокирует сборку при HIGH,
CRITICAL, UNKNOWN, обнаруженных секретах, неподдерживаемой ОС образа или ошибке
сканирования. Наличие исправления не влияет на блокировку: `ignore-unfixed`
не используется. LOW/MEDIUM остаются в локальном отчёте для рассмотрения.
Образы в `images.lock.json` — закреплённые кандидаты, а не обещание отсутствия CVE.
Официальный образ тоже может не пройти проверку. Флага обхода проверки нет.

## Схема

```text
Интернет ── существующий nft INPUT / ASN ── Nginx на хосте:443
                                              │ HTTPS завершается здесь
                                              ▼
                                     172.30.90.2:8080 Nextcloud
                                              │
                                     br-nc-back (internal)
                                       ├── PostgreSQL:5432
                                       └── Redis:6379
```

Docker не публикует порты: нет `ports:`, DNAT приложения, host networking,
Docker socket в контейнерах или privileged. Данные находятся вне webroot.
Код приложения, рабочая конфигурация и корневые файловые системы доступны только для чтения;
процессы работают не от root, без capabilities, с `no-new-privileges`,
ограничениями памяти/PID/CPU. Стандартные seccomp/AppArmor Docker сохраняются.
Apache ограничен четырьмя PHP workers по 512 МБ при лимите контейнера 3 ГБ;
масштабировать число workers и память нужно согласованно.
Nginx ограничивает одного клиента 32 одновременными запросами и 30 запросами/с
с кратковременным запасом 120; при превышении возвращает 429. За общим NAT эти
лимиты делят все пользователи. Это ограничение нагрузки, не защита от объёмного DDoS.

У Nextcloud отдельные сети front/back. База и Redis не имеют внешней сети.
Правила `bridge` фильтруют трафик внутри backend даже без `br_netfilter`.
Из приложения разрешены внешний HTTPS, DNS только выбранным резолверам и
HTTPS хоста для самопроверок. TCP 80/SMTP/LDAP, RFC1918, metadata endpoint и
доступ к другим портам хоста закрыты. Docker embedded DNS обслуживает имена
сервисов; ограничения DNS не являются защитой от DNS-туннелей.

Собственный домен внутри контейнера разрешается в gateway front-сети. Для него
Nginx получает отдельный listener на этом адресе и проверяет Host. Контейнеру
разрешён только этот адрес:443, чтобы self-check не открывал доступ к другим
vhost, защищённым внешней ASN-политикой. Не добавляйте другие сайты на этот listener.

IPv6 внутри контейнеров отключён; конфигурация vhost рассчитана на IPv4.
Для домена создайте A-запись. Не публикуйте AAAA до отдельной настройки IPv6.
Входящая политика основного firewall, включая ограничения ASN, сохраняется.

## Подготовка

Разместите репозиторий на сервере в `/opt/nextcloud` (владелец root, запись
только администраторам). Можно передать проверенную копию по SSH. Секреты,
рабочее состояние, отчёты и серверные nft-конфиги **не храните в Git**.
Для локальных конфигов предусмотрен игнорируемый каталог `local/`.

Установите недостающие утилиты штатным пакетным менеджером:

```bash
sudo apt-get update
sudo apt-get install --no-install-recommends python3 nftables iproute2 curl ca-certificates age
cd /opt/nextcloud
sudo ./tools/install-trivy.sh
sudo install -d -m 700 /etc/nextcloud-stack
sudo install -m 600 site.example.json /etc/nextcloud-stack/site.json
sudoedit /etc/nextcloud-stack/site.json
```

Скрипт установки Trivy использует фиксированную версию и SHA256 опубликованного
архива, без `curl | sh`. Проверка хеша защищает от подмены архива относительно
закреплённого значения; это не независимая проверка доверия к поставщику.
Обновляйте сканер вместе с его проверенными хешами.

В `site.json` укажите домен, администратора, внешний интерфейс, свободные /28
подсети, публичные DNS и **пути к существующему TLS-сертификату и ключу**.
Для relay с закрытым HTTP подходит ACME DNS-01. Установщик не читает и не
выводит ключ и не получает доступ к API вашего DNS-провайдера.
Продление сертификата и проверенный reload Nginx должны быть настроены на хосте.

В действующем `/etc/docker/daemon.json` должны быть явно заданы:

```json
{
  "iptables": false,
  "ip6tables": false,
  "userland-proxy": false
}
```

Это **фрагмент**, а не замена вашего файла. Docker/daemon.json, глобальные sysctl,
UFW, существующие nft-таблицы и сайты скрипт автоматически не перенастраивает.
Нужны `net.ipv4.ip_forward=1`, rootful Docker без userns-remap, стандартные
seccomp/AppArmor и Compose >=2.33.1.
Глобальный firewall должен быть готов до запуска приложения.

## Генерация и ручная интеграция nftables

```bash
sudo ./install.sh render
```

Файлы появятся в `/var/lib/nextcloud-stack/generated/`:

| Файл | Назначение |
|---|---|
| `nextcloud.nft` | Только таблицы Nextcloud: изоляция, egress NAT и bridge-фильтр |
| `filter-chains.nft` | Ограниченные цепочки для интеграции в основной filter |
| `input-jump.nft`, `output-jump.nft`, `forward-jump.nft` | Переходы из цепочек основного firewall |
| `nginx.conf` | Отдельный HTTPS-vhost |
| `security.config.php` | Настройки приложения, без значений паролей |
| `compose.json` | Docker Compose; до сборки образ приложения намеренно не существует |

`render` предназначен только для первоначальной подготовки и отказывается
перезаписывать конфигурацию установленного экземпляра. Каталог состояния должен
быть отдельным, принадлежать root и иметь права 0700; символические ссылки
в служебных путях и доступные посторонним на запись родительские каталоги запрещены.

`accept` в одной base chain **не отменяет drop в другой**. Поэтому при основном
firewall с policy drop одного `nextcloud.nft` недостаточно. В существующей
таблице `ip filter` подключите `filter-chains.nft`; в начале её input/output/forward,
перед общим `established,related accept` и антиспуфингом, подключите соответствующие
`*-jump.nft`. Нерелевантный трафик возвращается в исходную цепочку. Сам
`nextcloud.nft` подключите на верхнем уровне, после существующего `flush ruleset`,
если он есть в вашем полном конфиге.

Для конфигурации, которая уже содержит встроенные правила Nextcloud, повторные
include не нужны. **Не добавляйте глобальный `accept` для Docker-подсетей.**
Не заменяйте полный firewall только сгенерированным фрагментом.

Проверьте полный конфиг через `nft -c -f /путь/к/полному.conf`, затем примените
его своим обычным способом с резервной консолью/откатом. Сохраните правила в
постоянном конфиге: отдельная ручная загрузка таблиц потеряется при `flush ruleset`.
Не меняйте подсети или имена мостов после установки без согласованной миграции.

На общем IP nftables не различает HTTPS-vhost по домену. Если основной INPUT
допускает 443 только из разрешённых ASN, это относится и к Nextcloud. Открывать
443 всем или 80 для HTTP-01 установщик не будет.

## Установка

```bash
sudo ./install.sh preflight
sudo ./install.sh scan
sudo ./install.sh install
sudo ./install.sh nginx
sudo ./install.sh verify
```

`install` снова выполняет проверки перед сборкой: предыдущий отчёт не служит
разрешением на новую сборку. Порядок: актуальность выпуска → свежая БД Trivy →
сканирование всех трёх образов и исходников → проверка PHP → сборка без сети →
проверка готового образа → генерация секретов → создание БД → установка Nextcloud.
До завершения проверки контейнеры приложения не запускаются.

После установки включаются таймер cron и ежедневная проверка CVE. Автозапуск
через `nextcloud-stack.service` сравнивает фактические правила всех трёх таблиц
nftables с эталоном, включая порядок, выражения и политики; restart policy
Docker выключен, чтобы контейнеры не запускались раньше firewall. Если правила
загружает собственный systemd unit, добавьте его в `After=` службы Nextcloud.
Скрипт не запускает и не перезагружает nftables.service.
Команда `nginx` добавляет собственный systemd drop-in с `Wants/After=docker.service`:
Docker должен восстановить мост и его gateway до привязки Nginx к этому адресу
при загрузке хоста. Существующие файлы unit и drop-in без маркера проекта не заменяются.
Конфликт `server_name` считается ошибкой, даже если `nginx -t` вернул код 0.

Первичный пароль — `/var/lib/nextcloud-stack/secrets/admin_password`, каталог
доступен только root. Установщик не печатает пароли и не передаёт их через argv.
Compose secrets здесь — отдельные read-only bind mounts, **не шифрованное
хранилище**. Root и пользователи группы docker имеют полный доступ к данным.

Войдите по HTTPS, смените первоначальный пароль, настройте TOTP и сохраните
recovery codes вне сервера. Затем включите обязательную двухфакторную защиту:

```bash
sudo ./install.sh enforce-2fa
```

По умолчанию отключены публичные ссылки, публичная загрузка, resharing,
предпросмотры, магазин приложений и обновление через веб. Сброс пароля по почте
отключён до осознанной настройки SMTP; SMTP egress также закрыт. Это ограничения
данного профиля, которые нужно учитывать до выдачи доступа пользователям.
Дополнительные приложения следует включать в проверяемый образ, проверять
их зависимости и advisories, а не устанавливать в работающий контейнер.
Непустой `state/apps` блокирует запуск: ручное копирование приложения в этот
каталог не должно обходить проверку образа, даже если приложение выключено.
Квота файлов по умолчанию — 10 ГБ на пользователя. Её можно менять администратору
для конкретной учётной записи. Версии, корзина, БД и backup тоже занимают место:
квота пользователя не заменяет отдельный раздел для данных и мониторинг свободного места.

## Права каталогов и границы защиты

Пути хоста ниже приведены для стандартного `--state /var/lib/nextcloud-stack`.
Сам `state` имеет владельца root и права 0700, поэтому другие локальные пользователи
не могут пройти к его вложенным каталогам.

| Каталог/файл | Доступ работающего Nextcloud | Доступ через HTTP |
|---|---|---|
| `/srv/nextcloud` внутри образа | Чтение кода, без записи | Интерфейс и необходимые статические ресурсы; listing отключён |
| `state/config` — UID 33, 0700; `config.php` — 0600 | Только чтение | Не находится в webroot; `/config/` дополнительно закрыт |
| `state/data` — UID 33, 0700 | Чтение и запись | Только через API Nextcloud после проверки прав; `/data/` закрыт |
| `state/apps` — UID 33, 0700 | Только чтение | Только допустимые ресурсы приложений, без listing |
| `state/postgres` — UID 999, 0700 | Не подключён к Nextcloud | Недоступен |
| `state/secrets` — root, 0700 | Подключены только отдельные необходимые secrets, read-only | Недоступен |
| `/tmp` контейнера | Ограниченный временный tmpfs, `noexec,nosuid` | Недоступен как каталог |
| Файлы хоста, Docker socket, TLS-ключи, резервные копии | Не подключены к Nextcloud | Недоступны через Nextcloud |

В webroot нет даже символических ссылок на `config` и `data`: путь конфигурации
задаётся через `NEXTCLOUD_CONFIG_DIR`. Nextcloud создаёт новые пользовательские
файлы с маской 0077 и не следует символическим ссылкам в локальном хранилище.
Не копируйте пользовательские файлы вручную внутрь `data` и не меняйте владельцев
рекурсивно без проверки существующих данных.

Только кратковременный сервис `init` получает запись в конфигурацию для установки
и обслуживания; веб-приложение в это время остановлено. Административные операции,
которые меняют `config.php`, нельзя выполнять через обычный `docker compose exec app`.
`verify` проверяет права, Compose и файлы конфигурации, фактические mounts,
UID, capabilities, seccomp/AppArmor, лимиты и состав Docker-сетей.

Учётные записи Nextcloud разделяются проверками приложения. Все файлы обслуживает
один системный UID 33: успешное выполнение произвольного кода внутри Nextcloud
может дать доступ ко всем данным этого экземпляра и его учётным данным БД.
Изоляция ограничивает доступ к хосту и соседним сервисам, но не отменяет этого риска.
Root хоста и группа docker также имеют полный доступ. Исходящий HTTPS разрешён,
поэтому профиль не является защитой от вывода данных уже скомпрометированным приложением.

## Загрузка, копирование и синхронизация файлов

1. Пользователь входит через HTTPS. Для настольного клиента/WebDAV после включения
   2FA используется вход через браузер с выдачей клиенту отдельного пароля приложения.
   Такой пароль можно отозвать, не меняя основной пароль учётной записи.
2. При загрузке браузер или клиент передаёт файл в API Nextcloud. Nginx передаёт
   запрос Apache/PHP, затем Nextcloud проверяет пользователя, права и квоту.
   Файлы сохраняются в `data/<userid>/files/`, а сведения о них — в PostgreSQL.
   Redis обслуживает кэш и блокировки, а не хранит основную копию файлов.
3. Большие файлы поддерживающий это клиент загружает частями через WebDAV upload API.
   После получения частей сервер собирает файл; незавершённая загрузка не должна
   подменять готовый файл. В профиле лимит **одного HTTP-запроса** — 1 ГБ, поэтому
   для более крупных файлов нужен клиент с разбиением на части и свободное место
   для временных данных. Обычный WebDAV PUT больше лимита будет отклонён.
4. При копировании между папками Nextcloud клиент может отправить WebDAV `COPY`:
   сервер проверит права на источник и назначение и создаст копию без скачивания
   содержимого на компьютер пользователя. `MOVE` перемещает/переименовывает файл
   и обновляет метаданные. Перенос с компьютера в синхронизируемую папку, напротив,
   приводит к последующей загрузке на сервер.
5. Настольный клиент следит за выбранной локальной папкой и проверяет изменения
   на сервере. Через WebDAV он получает сведения о файлах и их ETag, загружает
   локальные изменения и скачивает удалённые. Изменение и удаление распространяются
   на остальные подключённые устройства; обычная синхронизация не является backup.
6. Если файл изменили независимо на двух устройствах, устаревшая условная запись
   отклоняется. Настольный клиент обычно сохраняет локальную конфликтную копию
   и скачивает серверную версию; пользователь должен сравнить и объединить их.
   Не рассчитывайте на автоматическое объединение содержимого произвольных документов.

Мобильная автозагрузка фотографий и настольная двусторонняя синхронизация имеют
разное поведение; удаление локальной фотографии зависит от настроек конкретного клиента.
Публичные ссылки в этом профиле выключены. Просмотр собственных каталогов через
авторизованный WebDAV необходим для синхронизации; прямое раскрытие файловой
системы сервера при этом не требуется.

HTTPS шифрует передачу, а `age` — резервные копии. Рабочие файлы на сервере этим
профилем автоматически не шифруются, сквозное шифрование не включено.
Клиентская синхронизация и Trivy также не являются антивирусной проверкой загружаемых файлов.

Справка: [WebDAV и загрузка частями](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/WebDAV/chunking.html),
[конфликты синхронизации](https://docs.nextcloud.com/server/stable/user_manual/en/desktop/conflicts.html),
[защита каталогов](https://docs.nextcloud.com/server/stable/admin_manual/installation/harden_server.html).

## Проверки безопасности и свежие advisories

Гарантировать проверку «всех возможных уязвимостей» невозможно: CVE-базы запаздывают,
есть zero-day, неподдерживаемые форматы пакетов и ошибки конфигурации окружения.
Trivy проверяет поддерживаемые OS/language-пакеты, секреты и Dockerfile;
структуру Compose и правила nftables дополнительно проверяют тесты проекта.
UNKNOWN блокируется консервативно и может потребовать анализа ложного срабатывания.
Отчёты — `/var/log/nextcloud-security/`, права 0700; в Git/CI artifacts не отправляются.

Включены отдельные проверки для уведомлений, актуальных на 27.10.2026:

- **CVE-2026-110447**, Built-in CODE Server: приложение исключено; наличие его
  файлов, даже у отключённого приложения, блокирует запуск. Nginx также запрещает
  доступ к этим каталогам. Исправление upstream — `richdocumentscode >=26.4.303`;
  простого отключения недостаточно. [Collabora advisory](https://github.com/CollaboraOnline/online/security/advisories/GHSA-g3vx-3m76-fghh).
- **CVE-2026-109618 / CVE-2026-109619**, PHP RCE: минимальные допустимые версии
  PHP — 8.3.36, 8.4.27, 8.5.12. Сам PHP собран из исходников в официальном образе,
  поэтому проверка не ограничивается списком OS-пакетов.
  [Уведомление PHP](https://www.php.net/archive/2026.php).
- **CVE-2026-115560**: принудительно отключён `session.upload_progress.enabled`,
  включая проверку получившегося образа.
  [Изменение Nextcloud Docker](https://github.com/nextcloud/docker/pull/2614).

Следите также за [официальными advisories Nextcloud](https://github.com/nextcloud/security-advisories/security/advisories).
Версия Nextcloud сверяется с текущим maintenance-релизом ветки 35; переход на
следующий major не выполняется автоматически. Проверка номера версии не заменяет
анализ вновь опубликованных advisories, особенно для дополнительных приложений.

## Обслуживание и обновление

```bash
sudo ./install.sh verify
sudo systemctl status nextcloud-stack.service nextcloud-cron.timer nextcloud-security.timer
sudo journalctl -u nextcloud-security.service
sudo ./install.sh stop
sudo ./install.sh start
```

Ежедневная проверка сообщает об ошибке через failed unit/journal. Она не отправляет
почту, не обновляет образы и не останавливает работающий сервис автоматически.
Подключите эту службу к существующему мониторингу. Также обновляйте Ubuntu,
ядро, Docker и Nginx: сканирование контейнеров не покрывает хост.

Теги в `images.lock.json` закреплены digest. `python3 tools/refresh-lock.py`
покажет актуальные digest официальных образов; `--write` заменит lock после
получения всех manifest и проверки их SHA256. Сравните изменения перед сборкой.
Major Nextcloud 35 / PostgreSQL 17 / Redis 8.2 сохраняются; `latest` не используется.
Обновление lock не означает прохождение проверки CVE. Затем:

```bash
sudo ./install.sh upgrade --destination /var/backups/nextcloud-before-update.tar.gz.age --recipient age1ВАШ_ПУБЛИЧНЫЙ_КЛЮЧ
```

Сначала проходят проверки и сборка, затем создаётся backup, включается maintenance
и выполняется миграция. При отказе сканера работающий экземпляр не изменяется.
После ошибки миграции возможен только согласованный restore БД и данных;
автоматического downgrade или удаления данных нет.
Маркер `upgrade-in-progress` запрещает обычный запуск незавершённой миграции.
Не удаляйте его, чтобы обойти ошибку; восстанавливайте согласованное состояние.

## Резервное копирование и восстановление

Ключ `age` создавайте на отдельной доверенной машине, приватную часть храните
вне сервера. Передавайте установщику только публичного получателя:

```bash
sudo ./install.sh backup --destination /var/backups/nextcloud-2026-10-27.tar.gz.age --recipient age1ВАШ_ПУБЛИЧНЫЙ_КЛЮЧ
```

Backup останавливает приложение на время копирования, использует `pg_dump`,
затем возобновляет работу. Архив содержит данные, config, секреты, dump БД,
конфигурацию запуска и сведения об образах. Поток tar шифруется через age;
временный dump доступен только root и удаляется после операции.
Конечное имя получает только полностью записанный зашифрованный архив;
при сбое незавершённый файл удаляется, приложение возвращается из maintenance.
Если снятие maintenance не удалось, исправьте причину перед возобновлением доступа.
Это не защита от root хоста; при необходимости используйте шифрование диска.
Отправляйте копию во внешнее хранилище, задайте расписание и проверяйте restore.

Восстановление выполняйте на **отдельном пустом стенде**, не поверх рабочего:

1. Установите ту же ревизию этого репозитория и сохраните доступ к исходным
   проверенным образам. В backup нет многогигабайтных Docker image archives.
2. Расшифруйте архив вне репозитория в root-only каталог: `age -d -i /путь/identity
   -o /защищённый/backup.tar.gz /путь/backup.tar.gz.age`. Не передавайте приватный ключ
   в аргументе строки и не выводите его. Проверьте список файлов перед распаковкой.
3. Восстановите `config`, `data`, `apps`, `secrets`, `site.json`, `generated`,
   `build.json`, сохранив числовых владельцев/права. В `generated/compose.json`
   абсолютные пути должны соответствовать новому состоянию. Восстановление на
   другой путь требует аккуратной регенерации конфигурации.
4. Создайте **новый** каталог `postgres`, принадлежащий 999:999 (0700), и запустите
   только `db` и `redis` из восстановленного Compose. Init SQL создаст роль приложения
   с исходным паролем и пустую БД. Не монтируйте старые физические PGDATA в другой major.
5. Восстановите dump через stdin:
   `docker compose -p nextcloud -f /var/lib/nextcloud-stack/generated/compose.json exec -T db
   pg_restore -U postgres --clean --if-exists --no-owner --role=nextcloud -d nextcloud < /защищённый/database.dump`.
6. Загрузите проверенные firewall-правила. Пока `app` остановлен, выполните
   `docker compose -p nextcloud -f /var/lib/nextcloud-stack/generated/compose.json run --rm --no-deps -T init /srv/nextcloud/occ maintenance:mode --off`
   и аналогично `maintenance:data-fingerprint`. Затем `./install.sh start`,
   `./install.sh verify`, `./install.sh enable-services`. Проверьте вход, WebDAV и контрольные суммы тестовых файлов.
   Только после этого восстанавливайте vhost и доступ пользователей.

Если исходные образы уже не проходят текущую CVE-проверку, восстановление сначала
проводится в закрытом стенде с последующим исправлением/обновлением. Приватный
ключ age, резервные копии, конфиг Nextcloud и сертификатные ключи не публикуйте.

## Тестирование

```bash
python3 -m unittest discover -s tests -v
shellcheck install.sh tools/install-trivy.sh container/redis.sh
sudo python3 tests/network.py
```

Сетевой тест сам создаёт отдельные network/mount namespaces. Он проверяет
разрешённые соединения и запреты реальными TCP-пакетами и не загружает свой
ruleset в namespace хоста. Опция `--firewall /путь/полного.conf` проверяет
интеграцию с локальным firewall; все его include должны существовать.
Отчёты и серверные конфиги остаются локальными.

GitHub Actions запускает проверки кода и сетевые тесты на Ubuntu 24.04 и 26.04.
Проверка образов остаётся обязательным отдельным этапом установки; зелёный CI
установщика не означает отсутствие CVE в образах.

Основа настроек: [hardening Nextcloud](https://docs.nextcloud.com/server/stable/admin_manual/installation/harden_server.html),
[Docker и ручной firewall](https://docs.docker.com/engine/network/packet-filtering-firewalls/),
[сканирование образов Trivy](https://trivy.dev/docs/latest/target/container_image/).
